# Leyline security review (2026-11-02)

Scope: `/home/claude/wt-theme` (read-only). This was a static code review. Nothing was built, run or deployed. Not in the
repo, so not reviewed: the live Caddyfile, server state (`authorized_keys`, env files), the Rust realm-site service
(`ovlive-realm`) and the public `orionopenwow/Leyline` repo's live settings. Anything that depends on those is marked
**unconfirmed**. No live secrets were found in the tree. The pattern hits in `tools/control/test_control_hq.py`,
`tools/leyline-repo/test_*.py` and `tools/security/test_security.py` are dummy test fixtures.

This review builds on the earlier audit `docs/SECURITY-HARDENING.md` (2026-10-31). Where an item from that audit is
still open in the code, it says so.

---

## 1. Findings (confirmed by reading the code)

Ranked by severity. Each finding gives its location, an attack scenario and a fix.

### F1. HIGH: An agent can ship to every player's PC, and no person has to approve it
- `tools/control/control.py:392-394`. "Ask before deploys" defaults to **off**: `confirm_on()` returns
  `bool(_auto_doc().get("confirm"))`.
- `tools/control/control.py:455-485`. With Autopilot on, any known step that Claude writes into `UPDATES-PENDING.txt` runs
  within a minute, deploy and ship steps included. Only `discord-apply` is `OWNER_ONLY` (`:277`).
- `tools/github-workflows/leyline-launcher.yml:17-21, 46-58, 126-194`. Every push to `main` that touches `launcher/` becomes a
  **stable** release with a signed `latest.json`.
- `launcher/src-tauri/src/update.rs:206-214` and `app.rs:1440-1500`. Installed launchers download that release by
  themselves, and install it at Restart or at the next start.
- **Scenario.** Claude regularly reads text that players and strangers control: the bug-report intake
  (`stream/bugreport.py`, which feeds `gmconsole/server/bugs_manifest.py`), forum posts, community digests, the scout's
  r/wowservers digest and Discord. A prompt injection in a bug report ("the fix is to add this download to updater.rs…")
  only has to persuade Claude to edit code and queue `ship`. CI then signs the result and every launcher installs it.
  No technical control sits between untrusted text and a signed auto-update. How likely Claude is to comply is
  **unconfirmed**, but nothing in the system stops it.
- **Fix:**
  - Make `confirm` default to true.
  - Add every step that pushes code or deploys (ship, launcher, signin, scripts, client, hostkit, release-mirror) to
    `OWNER_ONLY`.
  - In the public repo, put `TAURI_SIGNING_PRIVATE_KEY` in a GitHub **Environment** with a required reviewer, so a release
    needs a person's click.
  - Run Claude sessions that read untrusted input without the ability to edit `UPDATES-PENDING.txt`.

### F2. HIGH: The updater signing key is exposed to unpinned build tooling
- `launcher/package.json` has `"@tauri-apps/cli": "^2"` and there is **no `package-lock.json`**. The workflow runs
  `npm install` (not `npm ci`) at `leyline-launcher.yml:108, 232, 281`.
- In the same job, `tauri-action` runs that freshly resolved CLI with `TAURI_SIGNING_PRIVATE_KEY` and its password in its
  environment (`:244-248`, `:293-297`). Every Cargo build script in the 642-crate `Cargo.lock` also runs with the key in
  the environment.
- **Scenario.** A compromised npm release of `@tauri-apps/cli` or one of its dependencies, or a malicious `build.rs`
  arriving through a `cargo update`, reads the key and sends it out. The attacker can then sign "updates" that every
  installed Leyline accepts. `backup_pubkeys` is empty, so the key cannot be rotated without first shipping a new build.
- **Fix:**
  - Commit `package-lock.json` and use `npm ci`. Use `cargo build --locked`.
  - Build **unsigned** in one job. Sign in a separate, minimal job (only `minisign`/`tauri signer sign` on the artifacts
    it downloads) whose environment holds the key and runs nothing third-party.
  - Generate an offline backup key now and fill `branding.json updates.backup_pubkeys`.

### F3. HIGH (trust): The Windows exe is not Authenticode-signed, and players get no checksum or verifiable asset
- `leyline-launcher.yml:10` ("No code signing yet") and `:84-124`. Every push replaces the same rolling `launcher-latest`
  `Leyline.exe` (`gh release upload --clobber`). The asset has no `SHA256SUMS` and no detached signature, and its release
  notes tell players to click "More info, Run anyway".
- The website's main download button is that rolling exe (`stream/hub.py:3247`). `Open Leyline Launcher.bat:15-36` fetches
  it and runs it with no check.
- **Scenario.** Look-alike sites ("leyline-launcher.com", Discord DMs) ship a trojanised `Leyline.exe`. Players have been
  taught that a SmartScreen warning is normal for Leyline, so the warning protects no one. Because the asset is rolling,
  nobody can say "the hash of the release you downloaded was X".
- **Fix:**
  - Sign with Authenticode. Options: Azure Trusted Signing, SignPath's free plan for open-source projects, or a Certum
    open-source certificate.
  - Publish versioned assets plus a `SHA256SUMS` signed with minisign (the same updater key or a release key).
  - Point the website at the versioned asset, not at `launcher-latest`.
  - Sign the macOS app and notarize it.

### F4. HIGH (unconfirmed server state): The CI deploy key may still be a root shell
- `tools/github-workflows/realm-scripts.yml:96-109` uses `ssh … root@play.openvanilla.app` with `WU_DEPLOY_SSH_KEY`.
- `tools/security/ci-key-migrate.sh:2-6` is still marked **DRAFT** and describes today's key as "restrict only = a full root
  shell". This is the earlier audit's H3. The code fix exists, but there is no proof the server was migrated.
- **Scenario.** Anyone who can push to `main` of WrathUnleashed, or who steals that secret, gets root on production: the
  site, the realm, `portal.env`, the Hero Key SSO signing key and the Discord bot token.
- **Fix:**
  - Apply the migration and check that `authorized_keys` has `command="/srv/wrath/luaup-ci.sh"`.
  - Move the deploy job into a protected GitHub Environment.
  - Protect `main` (earlier audit, section 3.4).

### F5. MEDIUM: Any website can knock on the relay and hijack a player's shared-port login
- `hosting/relay/wurelay/relay.py:1149-1160`. `POST /api/realms/<id>/knock` has no Origin or CSRF check. `cors()`
  (`:974-982`) only decides whether the response may be **read**.
- `httpd.py:30-37` parses the body as JSON whatever its Content-Type. A `fetch(..., {mode:'no-cors', body:'{}'})` with
  `text/plain` is therefore a "simple request" that any page can send.
- Shared port 3724 routes by the most recent knock from the caller's IP (`relay.py:773-776`, `last_knock`).
- **Scenario.**
  1. A forum link or ad leads to a page that knocks the attacker's public realm.
  2. The victim's stock client with `set realmlist relay.leylinelauncher.com` now logs in to the **attacker's**
     authserver.
  3. The attacker gets the SRP6 transcript (A, M1) and can crack a password the player chose themselves offline. Or they
     show a fake copy of the realm the player expected.
  
  Players behind carrier-grade NAT (many share one public IP) are exposed to the same routing confusion by accident or
  on purpose.
- **Fix:**
  - On `knock` and `accounts`, require `Origin` to be one of `site_origins`/`play_origins` and require
    `Content-Type: application/json`.
  - Prefer the per-realm `auth_port` realmlist, which the launcher already has as `realmlist_port`.
  - Consider dropping the shared port for public realms.

### F6. MEDIUM: Blind SSRF from relays through self-signed mesh records
- `hosting/kit/tools/wunet/mesh.py:197-200`. A relay record is accepted when `host` is well-formed DNS syntax and
  `http` is `^https?://<host>(:port)?$`. Plain **http and any port** are allowed, and the host is never resolved or
  range-checked.
- `hosting/relay/wurelay/meshnode.py:141-142`. Any accepted relay record with `"mesh": true` becomes a gossip peer.
  Records are self-signed with a key anyone can make. `/api/mesh/push` accepts 200 records per POST, with a cap of
  120 per IP per minute (`:417-427`).
- **Scenario.** An attacker pushes a record whose host is `x.attacker.tld` resolving to `127.0.0.1`, `10.x` or
  `169.254.169.254`, with port 2019 (Caddy's admin API) or 8091 (the portal). Every mesh relay then makes `GET /api/mesh/…`
  and `POST /api/mesh/push` requests to internal services. The paths are fixed, which limits the damage, but the attacker
  also gets a fleet of relays that hammer any victim host.
- **Fix:**
  - Require `https://` on port 443.
  - Resolve the name and refuse non-global addresses (`ipaddress.ip_address(x).is_global`) **at connect time**, pinning
    the IP that was checked.
  - Only peer with nodes the seed registry has health-checked.

### F7. MEDIUM: The SOAP bridge can reset any account's password, and its password check is optional
- `stream/wrath_portal.py:501-503`. `BRIDGE_ALLOW` includes `"account set password "`, `"account delete "` and
  `"ban account "` with **no restriction on which account**.
- `:3855-3866`. `bridge_auth_ok` returns True for any password when `BRIDGE_PASS` is unset. The earlier audit's
  section 3.5 is an owner step, and it is **unconfirmed** that it was done.
- **Scenario.** A bug in the realm-site service, or any container that gets `BRIDGE_HOST`'s IP on
  `wenilla-realm_default`, sends `account set password <SOAP_USER or a GM account> …` and so gets the full AzerothCore
  console. The "Hero Key revoked" style protections do not help here.
- **Fix:**
  - Allow account verbs only for names the site makes (for example `^WR\d{6}$`).
  - Refuse any account with a GM level.
  - Fail closed when `BRIDGE_PASS` is empty.
  - (Unconfirmed) Check that AzerothCore treats a SOAP command containing a newline as a single command.

### F8. MEDIUM: A stolen launcher token can take over the account, and the token is plaintext on Windows
- `launcher/src-tauri/src/social.rs:172-179`. The token is a JSON file in the app folder. The code comment says
  "readable by this user only on Mac/Linux"; Windows gets no DPAPI protection.
- `stream/social.py:1597-1599` and `stream/herokeys.py:37-39, 891-897`. Approving a launcher hands it the **browser's
  website session**.
- `herokeys.py:554, 772-795`. With only the Bearer token, `herokey/new` mints a new Hero Key, which revokes the old one,
  and `game/login` returns the permanent game password. Neither asks for the current key or any step-up.
- **Scenario.** A common infostealer grabs `%APPDATA%\…\` files and calls `POST /wrath/api/social/herokey/new`. The
  player is locked out and the thief has the account, its friends and its realm logins.
- **Fix:**
  - Store the token with the `keyring` crate (DPAPI, Keychain, Secret Service).
  - Require a browser confirmation or the current key for `herokey/new` and `password`.
  - Email or notify the player in HQ and the launcher when a new key is made.
  - Bind tokens to a device id and expire them when unused.

### F9. MEDIUM: The catalog, Host pack and feature flags are unsigned, so the sha256 pin rides on the same channel
- `launcher/src-tauri/src/catalog.rs:14` (`all.json`), `mods.rs:1800-1817`, `host/pack.rs:22` (`hostpack.json` on a
  rolling GitHub tag) and `p2p/flags.rs:4-9`. Each "sha256 check" compares the download to a hash that came from the same
  site or release that supplied the URL.
- `launcher/branding.json:30`. `release_log.public_key` is `""`, so the signed release log, which would fix this, is
  not trusted yet.
- **Scenario.** Someone compromises the website, or the owner's HQ session. That only needs the owner's Hero Key or
  Google login, because there is no MFA or step-up on `/wrath/admin`. They then publish:
  - a catalog mod with a `d3d9.dll`, which needs one click of consent;
  - a Host pack whose scripts host PCs run through Docker;
  - flags that route players through attacker relays (`mesh_relays`).
- **Fix:**
  - Activate the release-log key.
  - Sign `all.json`, `hostpack.json` and `flags.json` with an offline Ed25519 key, and verify them in the launcher.
  - Add WebAuthn or TOTP step-up for owner and admin actions in HQ.

### F10. MEDIUM (player safety): Leyline downloads a game client from any link and runs its exe unchecked
- `launcher/src-tauri/src/clientimport.rs:1-21`. A direct https link to "your own backup zip" is downloaded and unpacked,
  then `clients::detect` adds it, and PLAY runs that folder's `Wow.exe`. Nothing compares the exe with known stock builds.
- `clienttorrent.rs:1-15`. Magnet and torrent downloads of whole clients sit behind a "testing" switch that any player can
  turn on in Settings.
- **Scenario.** "Fast repack! Paste this link into Leyline" leads to a trojanised `Wow.exe`. A trusted launcher starts it,
  which makes the attack more convincing than a bare exe.
- **Fix:**
  - Keep a table of SHA-256 hashes for the stock executables (5875, 8606 and 12340 builds). Warn loudly about, or refuse,
    an unknown executable.
  - Compile the torrent "testing" switch out of release builds.

### F11. MEDIUM (player safety): Native-code mods are code execution after one click
- `launcher/src-tauri/src/mods.rs:84-91, 1396-1409` and `listed.rs:12-16`. A `.dll`, `.asi` or `.exe` in the client folder
  installs after a one-time OK per file hash. That OK is the earlier audit's M6 improvement.
- The rule that a moderator reviews native code is server-side policy only (`stream/listings.py:23-25`,
  `listings-policy.json`, which the owner can change). The launcher installs `state: community` and `reviewed` entries the
  same way (`listed.rs:19-20`).
- **Scenario.** A listed mod passes review, or the policy is relaxed, and then ships a DLL that steals browser cookies
  and Hero Key files. The game sandbox does not apply to it.
- **Fix:**
  - Enforce on the client: refuse native files unless the entry is `reviewed` **and** signed (see F9).
  - Make the consent dialog show the file hash, a VirusTotal link and the reviewer's name.

### F12. LOW: Rate limits trust only the last X-Forwarded-For entry (unconfirmed, depends on the Caddyfile)
- `stream/wrath_portal.py:3059` uses the last XFF entry. That is right only while Caddy is the only hop. If the planned
  Cloudflare "orange cloud" goes on before Caddy's `trusted_proxies`/`client_ip_headers` setup (earlier audit 3.1, step 6),
  every visitor shares a Cloudflare IP bucket. One flood then rate-limits sign-in for everyone.
- **Fix:** Apply the Caddy setting first and add a startup self-test.

### F13. LOW: Updater manifest check-then-use gap, and no protection against frozen updates
- `update.rs:358-392` checks the manifest, then `app.rs:1460-1465` hands the URL to the plugin, which fetches it again.
  A mirror can serve a different manifest the second time and so skip the URL-prefix check. The signature check still
  holds, so the impact is low.
- A hostile mirror can also hold back updates indefinitely (a "freeze attack").
- **Fix:** Pass the already-checked bytes to the plugin, or verify the signed release-log entry for the version.

### F14. LOW: Leyline Control token handling
- `tools/control/control.py:1331`. The session token goes in the URL (`/?t=`) opened in the default browser, so it lands
  in browser history and in browser sync.
- `:64`. The token file is plaintext.
- `:59`. The Discord bot token is `tools/discord-leyline/token.txt` inside the workspace, which is `Desktop\Leyline`
  (`:43`). Desktops are often OneDrive-synced (`discord_leyline.py:1054` looks for the OneDrive Desktop), so the bot token
  may be in the cloud. **Unconfirmed.**
- The good news: Host and Origin checks (`:866-875`) block DNS rebinding and cross-site POSTs, the cookie is
  `SameSite=Strict`, the steps are a fixed list (`STEPS`, unknown steps refused at `:507`) and `_safe_dir`/`_safe_name`
  are sound. No localhost CSRF or command injection was found.
- **Fix:** Move the token to a fragment or a one-time code. Keep secrets outside the workspace (`%LOCALAPPDATA%`) and
  protect them with DPAPI.

### F15. LOW (design): Community relays and nodes see players' game traffic
- 3.3.5a encrypts only packet headers. A node (`nodes.py`) or a community relay can read chat and whispers. An
  attacker-run authserver can also collect SRP transcripts and crack them offline.
- Passwords issued by Hero Key SSO are 80-bit random (`stream/herokey_sso.py:12-21`), so they are safe. Passwords that
  players choose on join pages are not.
- **Fix:**
  - Default community realms to Hero Key SSO.
  - Say in the UI when traffic goes through a community node.
  - Keep the ban and kill feed responsive.

### F16. LOW: The portal may sign with variable-time pure-Python Ed25519
- `stream/herokey_sso.py:1-3, 49-60` falls back to `ed25519_pure.py` when `cryptography` is missing. The container is
  `python:3.12-alpine` with only the standard library (`stream/fastloop.sh` `docker run`), so the SSO site key is
  probably signed with variable-time code. A remote timing attack is theoretical. **Unconfirmed.**
- **Fix:** `pip install cryptography` in a pinned portal image.

### Checked and found sound
These are part of what a reviewer would ask about; they are not findings.
- **Launcher CSP and IPC.** `script-src 'self'` with a local UI only, so remote content never gets IPC
  (`tauri.conf.json:23`). Capabilities are minimal (`capabilities/default.json`). `innerHTML` is used only for constant
  SVG.
- **Opening URLs.** `open_url` only opens URLs the core listed itself and that pass `plain_https` (`app.rs:1049-1058`).
- **Deep links.** `leyline://` never acts without a click (`deeplink.rs:1-15`).
- **Archive extraction.** Zip-slip, symlink, case-twin and size checks (`mods.rs:125-288`), plus symlink-aware writes
  (`inside`, `mods.rs:1146-1162`).
- **Updater.** Signatures are always checked by the plugin, there is no downgrade, and download URLs are prefix-checked
  (`update.rs`).
- **Agents.** They cannot approve their own requests or bypass native consent (`agents.rs:1027`).
- **Den Lite.** Loopback only (`labs/den-lite/src/lib.rs:79, 202`).
- **Website.**
  - Strict nonce CSP (`wrath_portal.py:3081-3087`).
  - Consistent CSRF: Sec-Fetch-Site and Origin checks plus HMAC form tokens (`admin.py:3031-3072`, `forum.py:879-888`,
    `social.py:1567-1591`).
  - `safe_next` and every other redirect target sanitised (`profiles.py:431-437`, `hub.py:5147`).
  - Forum output escaped, with http(s)-only links (`forum.py:119, 190-200`).
  - No upload endpoints.
  - SSRF on listings limited to the code forges (`listings.py:298-313`).
  - Device-code phishing mitigated by making the player type the code (`social.py:1505-1565`).
  - Discord interactions signature-verified (`forum_discord.py:1002-1016`).
  - Generated `.bat`/`.sh` files safe because `NAME_RE` limits the characters (`hostflow.py:76`).
- **CI.** Actions pinned by SHA, no `pull_request_target`, PR jobs have no secrets.

## 2. Hardening recommendations (defence in depth, each tied to this code)

1. **Split building from signing in CI** (F2). Use a protected `release` environment with a required reviewer. The signing
   job only downloads artifacts and runs minisign. Add `npm ci` and `cargo build --locked`, and turn on Dependabot or
   Renovate for `Cargo.lock`.
2. **Activate the release log** (`branding.json:30`). Sign `all.json`, `hostpack.json`, `flags.json` and
   `realm-overrides.json` with it. Then a compromised website cannot push code (F9) or freeze updates (F13).
3. **Step-up auth in HQ.** Require WebAuthn (or TOTP) for owner and admin actions in `admin.run_action`, `hq.note.add`
   and the flags, staff and release actions. Today one stolen website session controls flags, staff and the "note to
   Claude" channel.
4. **Control (F1).** Default `confirm` to on and make deploy steps `OWNER_ONLY`. Show a diff summary, files and line
   counts, before "Launch all" runs `ship`. Write Autopilot decisions to an append-only log.
5. **Launcher secrets (F8).** Store the social token, any kept website session and the Den or host secrets with
   `keyring`. Put `"Leyline Hero Key.txt"` (`herokeys.py:FILE_NAME`) in Documents by default, not Downloads, and offer a
   "delete after saving to a password manager" hint.
6. **Relay (F5, F6).** Check Origin and Content-Type on every state-changing `/api/*` route. Resolve hosts and allow only
   global IPs for mesh and node health checks. Require https on port 443. Limit `/api/mesh/push` per signer key as well as
   per IP.
7. **SOAP bridge (F7).** Name allowlist, fail closed without `BRIDGE_PASS`, and a separate low-privilege SOAP account
   for the bridge (earlier audit 3.7).
8. **Domain fallback.** `addresses.rs:5-6` sends Bearer tokens and fetches the catalog from `openvanilla.app`
   "forever". Put both domains on auto-renew with registrar lock, monitor them, and plan a date to stop the fallback.
   Anyone who registers a lapsed domain gets tokens and the catalog.
9. **Client exe check (F10).** Keep known-good `Wow.exe` hashes. Show an unknown executable as "modified client" with a
   red banner, and never auto-PLAY it.
10. **Portal image.** Pin `python:3.12-alpine@sha256:…` with `cryptography` installed (F16). Add HSTS at Caddy if it
    is not there; the Caddyfile was not reviewed, so this is unconfirmed.
11. **Untrusted text reaching Claude.** Mark bug reports, forum, Discord and scout content as data in the tools that hand
    it to Claude. The MCP server already does this in `agents.rs:INSTRUCTIONS`; do the same for `bugs_manifest` and the
    digests. Never let those sessions write `UPDATES-PENDING.txt`.
12. **Bot and Control secrets** (F14). Move `token.txt` out of the synced workspace. Check that `Desktop\Leyline` is
    excluded from OneDrive.

## 3. Community safety and trust recommendations (the project's public face)

1. **Authenticode-sign `Leyline.exe` and the installers** (F3). Use SignPath's free open-source plan or Azure Trusted
   Signing. Then remove "click Run anyway" from the release notes (`leyline-launcher.yml:118, 181`) and from the README.
   Until then, say plainly that Leyline is unsigned and how to verify it.
2. **Versioned downloads with published SHA-256 and a minisign-signed `SHA256SUMS`** on every release, linked from the
   website's download button instead of the rolling `launcher-latest` (`hub.py:3247`).
3. **A VirusTotal link per release asset**, posted by CI in the release notes. Also a short "how to verify" page:
   `certutil -hashfile Leyline.exe SHA256` and `minisign -Vm`.
4. **Reproducible builds.** Use `--locked`, a pinned toolchain and `SOURCE_DATE_EPOCH`, and publish the commit SHA beside
   each hash, so a third party can rebuild and compare. Today's builds cannot be reproduced because `npm install` floats.
5. **A `SECURITY.md`** with a disclosure contact (security@ plus a PGP key or GitHub private advisories), a response
   window and a scope that covers the launcher, website, relay and Host pack. Today the repo has only
   `docs/SECURITY-HARDENING.md`.
6. **"We will never ask for your Hero Key" messaging** on the sign-in page, on the Hero Key page, in
   `Leyline Hero Key.txt` itself, in the in-game login glue, in Discord's welcome and on the forum. A Hero Key is a bearer
   password with no second factor.
7. **Official-link verification.** Publish one signed list of official domains, Discord invites and GitHub orgs, and show
   it in the launcher. Add a Discord bot rule for look-alike domains. In forum and Discord links, put an interstitial in
   front of domains not on the list ("you're leaving Leyline").
8. **Mod review badges that the client enforces.** Show "Reviewed by <moderator>, <date>", the file hashes and a
   VirusTotal link on every Workshop and listed mod. Native code installs only when reviewed (F11). Show "Community, not
   reviewed" in red for anything that writes outside `Interface/AddOns`.
9. **Realm reporting and transparency.** Put a one-click "Report this realm" in the launcher and website realm lists
   (`network.py` already has the backend). Publish a ban list. Badge realms that use Hero Key SSO ("your password is never
   shared with this host"). Warn when a community relay or node carries traffic (F15).
10. **Signed update manifests explained.** Publish the updater public key (`tauri.conf.json:53`) and the release-log key
    on the website and in the README, so community mirrors can be checked independently.

10. MEDIUM. A game client from any link or torrent is launched with no check of the exe's hash, and native DLL mods need
    only one click; review is enforced only on the server (`clientimport.rs:1-21`; `mods.rs:84-91`; `listed.rs:12-20`).

## Top 8 trust recommendations

1. Authenticode-sign the Windows exe and installers, and stop telling players to "Run anyway".
2. Publish versioned assets with SHA-256 values and a minisign-signed `SHA256SUMS`, and link those from the website, not
   the rolling exe.
3. Post a VirusTotal link per release asset, plus a short "how to verify your download" page.
4. Make builds reproducible (lockfiles, `--locked`, a pinned toolchain) and publish the commit SHA beside each hash.
5. Add a `SECURITY.md` with a disclosure contact and private GitHub advisories.
6. Say "We will never ask for your Hero Key" on every sign-in surface, in the key file and in Discord onboarding.
7. Publish one signed list of official domains, Discord invites and GitHub orgs, shown in the launcher, with a warning on
   off-list links in forum and Discord posts.
8. Show mod review badges that the launcher enforces (no native code unless reviewed and signed), and add one-click realm
   reporting with a Hero Key SSO badge.
